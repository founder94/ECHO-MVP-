## 1. 최상위 계약(LOCK)
> 명확하고 똑똑하게 사용자가 한 말을 정확히 이해하고, 그 이해를 바탕으로 사용자와 같은 결의 사람을 추천·매칭한다.

- 대화의 첫 목적은 RELATIONSHIP_INTENT(어떤 만남을 원하는지)이다. 첫 문장은 고정하지 않고 AI 가 만든다.
- 기본 루프: LISTEN → UNDERSTAND → ACKNOWLEDGE → REMEMBER → CURIOUS FOLLOW-UP
- 다음 질문의 출발점은 방금 사용자가 한 말이다.
  - 고정 질문 목록, 주제 순서, 질문 수 강제는 없다.
- 사용자가 질문하면 먼저 답한다.
- 사용자가 틀렸다·항의하면 이렇게 한다.
  - 매칭 정보로 저장하지 않는다.
  - 먼저 인정한다.
  - 이미 들은 말을 짚는다.
  - 고친 맥락에서 이어 간다.
- 끝나는 조건: 매칭에 충분히 알게 되면 자연스럽게 마친다. 제품 경험 기준은 「이제 조금 알 것 같아요 · 정리해 둘게요 · 당신이 잠든 사이」이고, 문장은 고정하지 않는다.
- 성공 기준 10개(대표 실제 휴대폰 사용 기준)는 다음과 같다.
  1. 정확히 이해
  2. 먼저 반응
  3. 질문에 답
  4. 재질문 없음
  5. 틀리면 바로 고침
  6. 엉뚱한 점프 없음
  7. 자연스럽게 이어짐
  8. 매칭 정보로 연결
  9. 빠름
  10. 비용 과하지 않음

## 2. core-0.1 이 하는 일
파일: `product/spike/core-20260925/core.mjs` 하나. 휴대폰 시험 페이지와 Golden 재생이 이 파일을 글자 그대로 같이 쓴다. 같은지는 검사로 대조한다.

| 누가 | 무엇을 |
|---|---|
| LLM(한 턴 1번 · 형식이 깨졌을 때만 1번 더) | 말의 종류(answer·ask·correction·repair·unsure·stop), 이해 한 문장, 먼저 하는 반응, 기억 후보(영역 + 짧은 요약 + 원문 인용), 틀린 것이 된 기억, 방금 말에서 궁금한 것 하나 또는 없음 |
| 서버(코어의 상태 함수) | 아래 표 |
| 마칠 때 LLM 1번 더 | 들은 것만으로 정리 + 짧은 마무리 |

서버가 소유하는 것:

| 항목 | 내용 |
|---|---|
| 사용자 원문 | 매 턴 |
| 최신 정정 | — |
| 사용자가 문제 삼은 AI 질문 | disputed |
| 들은 정보 | 상태 = 들음 · 사용자 확인 전 |
| 대화 상태 | talk → closing → done |
| 매칭 정보 충족 여부 | 네 영역: 원하는 만남 · 편하거나 끌리는 사람 · 관계에서 중요한 것 · 알아가는 속도와 방식 |

- 네 영역은 방향으로만 준다(순서 없음 · 질문 문장 아님). 모두 들으면 서버가 대화를 마친다.
- 서버가 AI 출력에서 보는 것은 세 가지다.
  1. JSON 형식
  2. 제품 금지어(데이팅 등 6개)
  3. 기억의 원문 인용이 사용자 말에 그대로 있는지
- 3번은 질문 심사가 아니다. AI 가 지어낸 사실이 매칭 정보가 되는 것을 막는 장치다.
- 질문 문장 자체는 심사하지 않는다(글자쌍·n-gram·정규식 0).
