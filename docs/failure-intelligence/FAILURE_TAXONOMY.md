# ECHO Failure Taxonomy (v3 · 2026-09-25)

모든 실패는 **Failure Type**(무엇이 잘못 보였나) 하나 이상과 **원인 Layer**(어디서 생겼나) 하나 이상으로 분류한다.
실패 하나마다 정규식 하나를 더하는 식으로 고치지 않는다. 먼저 Layer 를 가른다.

## 1. 원인 Layer

| Layer | 뜻 | 이 층에서 고치는 방법 | 대표 사례 |
|---|---|---|---|
| Context | 모델이 받은 입력에 필요한 것이 없거나, 없어야 할 것이 있었다 | 입력 구성(최근 대화 · 정정 · 거절 · 답한 의도 · 목적). 남은 수·주제 순서 제거 | GF-04, GF-19 |
| Orchestration | 서버가 모델 후보를 잘못 막거나 잘못 통과시켰다. 규칙이 모델보다 먼저 잘못 결정했다 | 서버는 저장·정정·거절·의도·안전·상태만 결정. 문자열 품질 검사 금지 | GF-01~03, 05~08, 10~12, 14, 18 |
| Product Contract | 제품 규칙 자체가 기준본과 다르다 | 대표 결정 → 계약 수정 | GF-09 |
| Model | 같은 좋은 입력을 줘도 모델이 틀린다 | 같은 B 구조로 모델 비교(GPT/Claude/Gemini) — 대표 승인 뒤 | **아직 분리된 사례 0** |
| Infrastructure | 배포·네트워크·지연·자동 재요청·환경 | 배포 과정 · 지문 대조 · 시간 상한 | GF-11, GF-13(배포 누락), GF-20 |
| Evaluation | 검사가 실제 실패를 잡지 못하거나 통과로 셌다 | 실제 문장 재생 · 실AI Replay · 검사 역검사 | GF-15, GF-16, GF-17 |

- Model Layer 는 Context·Orchestration 을 먼저 정리한 뒤에만 판정한다.
  - 운영 A 의 실패는 입력(GF-04)과 서버 검사(GF-01·02)가 이미 불리한 상태에서 났다. 그래서 모델 탓으로 분리되지 않는다.

## 3-0. 방어 수준(대표 헌장 J · 차례대로만 올린다)

`HYPOTHESIS` → `CANDIDATE` → `MOCK_VERIFIED` → `REAL_AI_VERIFIED` → `USER_VERIFIED`

- 실제 AI 가 필요한 항목은 가짜 AI 통과만으로 REAL_AI_VERIFIED 가 될 수 없다.
- 실기기가 필요한 항목은 실기기 확인 전에 USER_VERIFIED 가 될 수 없다.
- 데이터 검사가 근거 파일 없는 승격을 막는다(`fi.test.mjs`).
- 원인 확신은 따로 적는다: `CONFIRMED`(기록·코드로 확인) · `MIXED`(일부 확인) · `HYPOTHESIS`.

## 3. 상태(Lifecycle)

```
OBSERVED → REPRODUCED → ISOLATED(원인 Layer 분리) → EXPERIMENTED(해결 실험)
        → REVERSE-CHECKED(정상 사례 역검사 · 해결 장치 일부러 망가뜨려 검사가 잡는지)
        → REAL-AI-VERIFIED(실제 AI Replay 통과) = VERIFIED
```

| 상태 | 뜻 |
|---|---|
| UNRESOLVED | 원인은 알았거나 모르지만 운영에서 해결되지 않았다 |
| MITIGATED | 운영에서 완화 조치를 했다. 실AI 재검증·정상 사례 역검사를 다 거치지 않았다 |
| RESOLVED | 검사 도구·배포 과정처럼 AI 품질이 아닌 결함을 고치고 확인했다 |
| VERIFIED | 위 lifecycle 끝까지 통과한 해결책이 있는 실패(현재 0) |
| FAILED_SOLUTION | 시도했으나 새 실패를 낳거나 효과가 없던 해결책 → `FAILED_SOLUTIONS_ARCHIVE.md`, 지우지 않는다 |

## 4. 출처 표시
- **ACTUAL**: 운영 기록 또는 대표 실기기 입력. 근거 문서 경로를 반드시 적는다.
- **ACTUAL(캡처 재구성)**: 대표 화면 캡처에서 옮김. 원문 일부가 빠졌을 수 있다.
- **FOUNDER_STATEMENT**: 대표가 지시·보고에서 말로 설명했지만 로그·원문이 없는 실패. ACTUAL 로 올리지 않는다.
- **REAL_AI_SCRIPTED**: 운영 서버 + 실제 AI 인데 사용자 말은 검사 계정의 스크립트 문장(캐너리·100회 검사). 모델 출력은 실제, 사용자 입력은 실제가 아니다.
- **SYNTHETIC**: 예문·대체 입력. 실제 사용자 입력이 아니다.
- **코드 확인**: 사용자 사례 없이 코드로 확인한 결함.
- 결과 표시: **[MOCK]** 가짜 AI · **[REPLAY]** 실제 문장을 서버 코드에 재생(AI 호출 0) · **[REAL]** 실제 AI.
  - [MOCK] 통과는 [REAL] 통과가 아니다.

## 5. Failure Family (`data/families.json` · 16개)

같은 모양의 실패는 원본을 지우지 않고 Family 로 묶는다.

| Family | 이름 | 지켜야 할 원칙 |
|---|---|---|
| F-REPEAT | 같은 뜻 반복 · 반복설명 강요 | 이미 들은 말·이미 물은 뜻을 다시 요구하지 않는다 |
| F-GUARD | 과잉 Guard(서버가 정상 후보를 죽임) | 서버는 질문의 취향을 평가하지 않는다 · 질문은 선택사항 |
| F-CLASSIFY | 말의 종류 오분류(답·되물음·항의·정정) | 한쪽으로 기운 규칙·기본값을 두지 않는다 |
| F-CONTEXT | 맥락 유실·오염·거절 재등장 | 최근 대화·정정·거절을 서버가 소유하고 매 턴 전달 |
| F-DRIFT | 방향이탈 · 무거운 질문 | 질문 출발 = 방금 정상 답 · 숨은 목차 금지 |
| F-SENTENCE | 문장 파손 | 사용자 말을 질문 문장에 끼워 넣지 않는다 |
| F-CONTRACT | 제품 계약 불일치 | 기준본과 다른 규칙은 대표 결정으로만 바꾼다 |
| F-EVAL | 평가 결함(가짜 통과) | 가짜 AI 통과는 실제 통과가 아니다 · 실제 문장 재생·실AI 로 확인 |
| F-DEPLOY | 배포·운영 과정 결함 | 검사한 파일 = 운영 파일(지문 대조) |
| F-PROMISE | 없는 기능·가짜 결과 약속 | 없는 기능을 있는 것처럼 보이지 않는다 |
| F-FLOW | 대화 구조(끝 없음·출구 없음·버튼 피로) | 끝·빠져나갈 문·중간 저장이 있어야 한다 |
| F-ANSWER | 사용자 질문에 먼저 답하지 않음 | 물으면 먼저 답한다(ANSWER FIRST) |
| F-STATUS | 정보 상태 오류(미확정 사실화) | 사용자가 확인한 것만 사실 · 상태는 서버 소유 |
| F-STATE | 서버 상태 결함(질문 소실·단계 오류·전달 실패) | 저장·전환은 말의 종류와 결과를 확인한 뒤 |
| F-LATENCY | 지연·시간 초과 | 한 턴 호출 수를 줄이고 실패는 빨리 알린다 |
| F-ADVISOR | AI 조언자(개발 AI) 실패 | 완료·결정·막힘·대기를 먼저 대조하고, 대표를 중계자로 쓰지 않는다 |
