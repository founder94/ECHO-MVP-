## 1. 질문 무한 반복의 원인 — 코드로 확정
- 대표가 휴대폰에서 쓴 core-0.1(`product/spike/core-20260925/core.mjs`)의 끝 조건은 `finish = stop || enough(st)` 였다. `enough` 는 네 영역을 모두 들었는지다.
- 모델은 기억을 intent·person 두 영역에만 넣었다. pace 는 0번이었다.
- 질문 수 상한도 없었다. 당시 계약 A-19 가 「질문 수 강제 금지」였다.
- 그래서 대표 세션이 13턴, 8턴이 되도록 끝나지 않았다.
- 프롬프트는 「방금 말에서 한 단계 더」를 가장 강하게 지시했다. 그래서 「편함」 한 주제만 파고들었다.
- 넘기기(skip)라는 종류가 없어 「다음질문으로 넘어가」가 반영되지 않았다.
- 증거: `evidence/FOUNDER_PHONE_TEST_20260925/README.md` · 실패 GF-78~82 · 실패한 해결책 FS-24

## 2. 반말의 원인
- 말투를 사용자가 고를 수 없었다.
- 프롬프트는 「해요체」 한 줄뿐이었다. 사용자 말투(「웅」·「있지」)를 따라가지 말라는 지시도 없었다.
- 첫 질문 「어떤 만남을 원해?」는 대표가 말하기 전에 이미 반말이었다. 모델(Claude 빠른 등급)이 약한 지시를 어긴 것이다(GF-83).
- 같은 시험에서 「RELATIONSHIP_INTENT」가 첫 질문으로 나왔다. 내가 프롬프트에 넣은 내부 이름이 새어 나온 것이다(GF-84, 내 실수).

## 3. v1.1 에서 바꾼 것
| 명세 | 구현 |
|---|---|
| 핵심 질문 최대 5 · 목적 5개 · 고정 문장 0 | 목적 5개(relationship_intent · attraction_comfort · values_character · relationship_style · boundaries). 목적마다 핵심 질문 1번. 한 답이 여러 목적을 채우면 그 목적은 묻지 않는다. 질문 문장은 AI 가 직전 답을 보고 만든다 |
| 꼬리질문 0 · 되묻기 최대 1 | 되묻기는 뜻을 알 수 없는 답(answer) 뒤에만, 대화 전체 1번. 모르겠다·넘기자·항의 뒤에는 되묻지 않는다 |
| 넘기기·어렵다·다른 거·그 질문 말고 → 주제 끝 | skip → 현재 목적 SKIPPED · 다음 목적. unsure → 모름으로 두고 다음 목적 |
| 질문 많다·그만 | stop → 들은 만큼 정리하고 마침 |
| 질문하면 먼저 답 | ask → reply 에서 먼저 답(서비스 사실 4개 안에서만) |
| 정정·거절·항의는 매칭 답으로 저장 안 함 | answer·correction 만 저장한다. correction·repair 는 틀린 기억을 거두고 직전 질문을 「문제 삼은 질문」으로 남긴다 |
| 말투 3종 · 기본 편한 존댓말 · 끝까지 유지 | 시작 전에 고른다. 매 턴 AI 입력에 규칙과 결 예시(질문 예시는 두지 않음)를 넣고, 「사용자가 다른 말투를 써도 지킨다」를 준다. 관측용 말투 판별은 막지 않고 기록만 한다(HEURISTIC) |
| TEXT/VOICE 같은 에이전트 | 같은 `agent.mjs` 상태·기억. VOICE 는 입출력만 다르다(VOICE_RESEARCH 참고) |
| 매칭 프로필 CONFIRMED/INFERRED/UNKNOWN | 원문 인용이 있는 것만 CONFIRMED. AI 추측은 INFERRED 로 따로 두고 매칭에 쓰지 않는다. MBTI·혈액형은 사용자가 직접 말했을 때만(인용 확인) |
| 매칭 handoff · 가짜 후보 금지 | `matchingHandoff` → `status: TEST_NOT_CONNECTED`, `candidates: []`, 기준 = CONFIRMED 만 |
| 한 턴 모델 1개 | 한 턴에 1번. 아래 경우만 한 번 더(최대 2) + 마칠 때 1번. 두 번째도 같으면 그대로 두고 기록만 한다 |

한 번 더 청하는 경우는 모두 상태·JSON 칸 약속 확인이다. 질문 문장의 좋고 나쁨을 심사하지 않는다.
- JSON 형식이 깨짐
- 반응(reply)에 물음표가 있음
- 이미 물은 목적을 고름
- 물을 목적이 남았는데 질문이 없음

## 4. 관리자 화면 — 대표 전용 시험 페이지 안
- 권한: 페이지 db 규칙(읽기·쓰기 = 편집자 이상)이 서버에서 막는다. 화면 버튼은 소유자에게만 보이지만, 그건 편의일 뿐 보호가 아니다.
  - `as_level: interact` 로 읽어 보니 0건이었다(막힘 확인).
- 화면은 다섯 가지다.
  - 대시보드
  - 대화 보기(턴마다 원문·ECHO 문장·질문 진행·답한 목적·종류·표시·모델 등급·지연·오류·재요청)
  - 매칭 프로필(목적별 상태·추측·정정·거절·MBTI/혈액형·매칭 상태)
  - 실패·성공 후보(자동 · CANDIDATE · 증거 ACTUAL/HYPOTHESIS)
  - AI 관측(경로별 호출·오류·잘림·p50/p95 · 토큰·비용 = 확인 불가)
- 쓰기 호출은 0이다. 검사로 막는다. 옛 core-0.1 시험 문서도 그대로 읽는다(대표 기록 2건).
- **운영 관리자(/doit/admin/mobile)에는 연결하지 않았다.** 에이전트가 운영에 없고, 관리자 전체 읽기 정책은 PENDING SQL(실행 금지)이다. 장부 B-10.
