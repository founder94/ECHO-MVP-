## B. 현재 문제 (7개, 하나도 "괜찮다"로 바꾸지 않음)

1. **동의 기록이 사라진다.** 동의 판(`profiles.consent_version`)과 연결 동의(`user_metadata.doit_connect_consent_*`)가 계정과 함께 삭제된다. 약관 동의 **시각**은 원래 저장되는 칸이 없다. 기존 초안 `PENDING_20260921_user_consents.sql` 도 `on delete cascade` 라 같은 문제가 있다.
2. **신고 기록이 대상을 잃거나 삭제된다.** 신고자가 탈퇴하면 신고 줄 삭제(CASCADE). 신고 대상이 탈퇴하면 대상 칸이 NULL(누구였는지 모름). 근거가 된 연결·이야기(doit_matches·messages)도 CASCADE 로 삭제.
3. **결제 보관이 계정 삭제에 묶여 있다.** 앱 탈퇴는 결제가 있으면 멈춰서 지금은 막혀 있지만, 이메일 요청을 받아 관리자가 대시보드에서 지우면 결제 기록까지 삭제된다. 지금은 결제 0줄이라 실제 피해는 0.
4. **KEY 표는 탈퇴 뒤에도 남는다.** FK 가 없어 CASCADE 가 안 걸리고, doit-account 도 이 표를 지우지 않는다(9줄, 한 계정).
5. **재가입으로 신고·차단을 피할 수 있다.** 새 가입 = 새 UUID. 옛 UUID 에 걸린 차단(blocks)은 CASCADE 로 사라지고, 신고는 대상 NULL. 이메일·전화 기준 재가입 확인 장치가 없다(전화 인증 0명).
6. **약관과 코드가 다르다.**
   - 처리방침 "탈퇴 시 지체 없이 파기 … 다만 전자상거래법 5년·3년, 통신비밀보호법 3개월 보관" → 코드에는 **분리 보관 장소가 없다**(전부 삭제 또는 결제 있으면 탈퇴 불가).
   - 처리방침 1항 "그만하기·차단·신고 기록"을 수집한다고 적었지만 탈퇴하면 이 기록이 같이 지워진다(보관한다는 말은 없어 모순은 아니지만, 제재 목적과 충돌).
   - 이용약관 65행 "연결된 상대 화면에서도 연결이 사라집니다" = 코드와 **일치**(CASCADE).
7. **접속 기록 3개월 보관을 어디서 지키는지 확인 불가.** `auth.audit_log_entries` 0줄. Supabase 플랫폼 로그·Netlify 로그의 보관 기간은 요금제에 따라 다르고 이 환경에서 확인하지 못했다(검증 필요).

## D. 권장 최종 구조 (초안 · 법무 확정 전)

**원칙:** 계정·답·사진·대화는 지금처럼 즉시 삭제한다. 법적으로 필요할 수 있는 것만 **계정과 끊긴 별도 표**에 **최소 칸**으로 옮기고, 모든 보관 줄에 **만료일을 필수**로 둔다(무기한 금지).

### D-1. 지워지는 데이터 (현재와 같음)
계정(auth.users·세션·패스키), 프로필, 답·이해·요청 기록, ECHO 시절 대화, 사진 표·파일, 연결·첫 답·이야기, 차단, KEY 표(**추가: 서버가 명시적으로 삭제**), 브라우저 저장소.

### D-2. 분리 보존되는 데이터
| 보관 표(초안) | 옮기는 칸 | 옮기지 않는 것 | 기간 |
|---|---|---|---|
| `withdrawal_consent_evidence` | 옛 계정 번호, 동의 판, 동의 시각(있을 때), 연결 동의 판·시각, 탈퇴 시각 | 이메일·전화·이름 | `retain_until` 필수, 값은 L1 확정 뒤 |
| `payments`(FK 를 SET NULL 로) | 주문 번호·금액·상태·승인 시각·옛 계정 번호 | 이메일 | `retain_until`, L4 확정 뒤 |

### D-3. 신고·제재 데이터
- `user_reports.reporter_id` CASCADE → **SET NULL**(신고가 사라지지 않게).
- `reporter_former_user_id`·`target_former_user_id` 칸 추가 — 탈퇴 직전 서버가 채움(누구였는지 계정과 끊긴 번호로 남김).
- 신고 근거 문장(이야기) 보관 여부는 L2 확정 전까지 **보관하지 않음**(지금처럼 삭제).

### D-4. 재가입 처리
- **제재가 확정된 계정만**(신고 처리 완료 상태), 탈퇴 직전 이메일(과 전화, 있을 때)을 정규화 → `HMAC-SHA256(pepper, 값)` 만 `withdrawal_identifier_holds` 에 저장. **원문 저장 금지.**
- 가입 시 같은 HMAC 이 있으면 "관리자 확인 대기"로 두고 자동 거절하지 않는다(빠져나갈 문 — 오탐·가족 공용 메일 대비).
- `expires_at` 필수(무기한 금지), 기간은 L3 확정 뒤. 만료되면 `withdrawal_purge_expired()` 로 파기.
- pepper 는 서버 비밀값(Secret) — 만들거나 바꾸는 것은 STOP 게이트.
- 제재가 없는 일반 탈퇴자의 식별값은 **저장하지 않는다.**

### D-5. 7일 비활성화 후 삭제형 — 후보로만
- 달라지는 것: 탈퇴 요청 = 로그인·연결 노출 즉시 중지 + 삭제 예정 시각 기록 → 7일 뒤 스케줄이 D-1 수행. 그 사이 취소 가능.
- 새로 필요한 것: 상태 칸(profiles 또는 별도 표), 예약 삭제 스케줄(pg_cron 또는 예약 함수), 비활성 계정을 후보·연결·로그인에서 빼는 검사 전부(같은 모양 코드 전수), 약관 문구(L8).
- 위험: 7일 동안 개인정보가 남는다, 스케줄 실패 시 삭제 누락 → 실패 알림 필요.
- **구현하지 않았다.**

## H. 되돌리기 방법
- **DB 초안:** 파일 끝 "되돌리기" 블록(새 표·함수 삭제, FK 를 CASCADE 로 복구, 추가 칸 삭제). 보관 중인 증빙도 같이 지워지므로 보관 기간 중이면 되돌리기 전에 법무 확인. NOT NULL 복구는 NULL 줄이 없을 때만.
- **doit-account:** 운영 버전 1 원본(SHA-256 `97af5498…`)으로 재배포. 새 단계는 모두 deleteUser **앞**에서 실패하면 멈추므로, 되돌려도 반쯤 지운 계정은 생기지 않는다.
- **가입 확인:** 확인 단계를 끄면 예전 가입과 같다(보류 표는 남음).
- **약관:** 이전 판 문장으로 되돌림. LEGAL_VERSION 을 올렸다면 되돌리지 말고 새 판으로 고침(동의 기록 혼동 방지).
