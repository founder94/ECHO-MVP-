## 먼저: 조사 중 새로 확인된 사실 (GAP-16)

**Purpose 진실 원천이 세 곳이고 서로 다르다. 이미 운영 데이터가 어긋났다.**

| 출처 | 개수 | 예시 |
| --- | ---: | --- |
| DB `purposes` (활성) | 4 | friend "친구를 만나고 싶어요" · romantic "연애로 이어질 만남을 원해요" |
| 프론트 `PurposeSelect.tsx` 하드코딩 | 12 | friend "친구 관계" · romantic "이성 관계" · values "가치관 기반 관계" |
| `mocks/do-it.ts` | 별개 | slow "사람을 천천히 알아가기" |

실제 저장된 값 (profiles 5명 중 2명):

| 저장된 purpose_id | 저장된 label | DB purposes 에 존재? |
| --- | --- | --- |
| `values` | 가치관 기반 관계 | **없음** |
| `romantic` | 이성 관계 | 있음 (단 label 불일치) |

`spaces.purpose_id → purposes` 외래키가 이미 걸려 있으므로,
`values` 같은 id로는 나중에 목적 공간을 만들 수 없다. 가입 직후 데이터가 이미 갈라졌다.

## 1. P0 — 지금 반드시 막을 것 (3건)

### GAP-01 · Plan A 자기이해가 서버에 저장되지 않음
- **현재**: 빌드 스위치 `VITE_A_STRUCTURE_SERVER_ENABLED`가 꺼진 채로 나가서, 사용자가 남긴 기록과 통찰이 브라우저(localStorage)에만 저장된다.
- **필요**: 서버 저장. 재로그인·다른 기기·브라우저 정리 후에도 복원.
- **왜 지금**: ECHO의 제품 가치가 자기이해 데이터 축적인데, 그 데이터가 사라진다. 사용자가 쓸수록 잃는다.
- **부족한 층**: FRONT (빌드 환경변수 1줄)
- **위험도**: P0 — 사용자 데이터 유실
- **기존 자산 재사용**: 100%. Edge `doit-understanding` v4, 테이블 `doit_records`/`doit_insights`, RPC 7개 모두 완성되어 있고 과거 데이터 591건이 실제로 쌓였다.
- **대표 승인 필요**: 예 (빌드·배포)
- **구현 우선순위**: 1 · 범위 S

### GAP-16 · Purpose 진실 원천 3중 충돌 (신규)
- **현재**: 화면은 12개 하드코딩 목록을 보여주고, DB에는 활성 4개만 있다. 같은 id인데 문구가 다르고, DB에 없는 id가 이미 저장됐다.
- **필요**: DB `purposes`를 유일한 목록으로 쓰고 화면은 조회만 한다.
- **왜 지금**: 이미 어긋난 데이터가 생겼다. 공간·관계를 만들기 전에 잡지 않으면 그 위에 쌓인다. 외래키가 이미 걸려 있어 나중에 더 비싸진다.
- **부족한 층**: FRONT (조회로 교체) + DB (기존 2건 정리 판단)
- **위험도**: P0 — 데이터 무결성
- **기존 자산 재사용**: DB `purposes` 테이블·정책 그대로. 읽기 정책이 이미 전체 허용이라 서버 작업 없음.
- **대표 승인 필요**: 예 (어느 목록이 맞는지 대표가 정해야 함 — 아래 PHASE 3 목록 참조)
- **구현 우선순위**: 1 · 범위 S

### GAP-15 · `is_admin()`이 비로그인에게도 열려 있음
- **현재**: `anon` 역할이 `/rest/v1/rpc/is_admin`을 호출할 수 있다.
- **필요**: `authenticated` 한정.
- **왜 지금**: 지금은 정보가 새지 않는다(로그인 안 했으면 false 반환). 그래도 관리자 판별 함수를 비로그인에 열어둘 이유가 없다. 고치는 비용이 거의 없다.
- **부족한 층**: RPC 권한 1줄
- **위험도**: P1이지만 비용이 낮아 P0 묶음에서 함께 처리 권장
- **기존 자산 재사용**: 함수 로직 그대로. 권한만 회수.
- **대표 승인 필요**: 예 (DB 권한 변경)
- **구현 우선순위**: 1 · 범위 S

## 2. P1 — MVP 출시에 반드시 필요한 것 (3건)

ECHO Plan A의 최소 사용자 가치 고리는 **"나를 남긴다 → 같은 목적의 사람과 이어진다"**이다.
그 고리를 완성하는 데 꼭 필요한 것만 남겼다. 공간·관계 7단계를 전부 만들지 않는다.

### GAP-02 · 공간 참여 (Membership)
- **현재**: `spaces` 테이블은 있으나 0행이고, 누가 어느 공간에 있는지 담을 테이블이 없다.
- **필요**: 사용자–공간 연결, 입장·나가기, 중복 입장 방지, 정원 관리.
- **왜 필요**: 이게 없으면 두 사람이 만날 자리가 없다. 관계 기능 전체의 바닥이다.
- **부족한 층**: DB · RLS · SERVER · STATE
- **위험도**: P1
- **기존 자산 재사용**: `spaces` 테이블 구조(purpose_id FK, max_members, is_locked)를 그대로 쓴다.
- **대표 승인 필요**: 예 (새 테이블)
- **구현 우선순위**: 2 · 범위 M

### GAP-06 · 상호 선택
- **현재**: 테이블 없음.
- **필요**: A와 B의 선택을 각각 저장하고, 서버가 트랜잭션 안에서 양쪽 일치를 판정한다. 선택 전에는 서로 안 보인다.
- **왜 필요**: ECHO가 기존 앱과 다른 지점이 여기다. 한쪽이 일방적으로 연결하지 않는다.
- **부족한 층**: DB · RPC · RLS · STATE
- **위험도**: P1. 구현 시 동시 요청(둘이 같은 순간에 선택) 처리가 핵심.
- **기존 자산 재사용**: `key_spend` RPC의 설계 패턴(advisory lock + 멱등 키 + 트랜잭션)을 그대로 따라 쓸 수 있다. 이미 검증된 방식이다.
- **대표 승인 필요**: 예 (새 테이블 + RPC)
- **구현 우선순위**: 2 · 범위 M

### GAP-07 · 관계 열기
- **현재**: 테이블 없음.
- **필요**: 상호 선택이 맞은 두 사람의 관계 행 1개, 상태값, 중복 생성 방지.
- **왜 필요**: 상호 선택의 결과를 담을 곳이 없으면 선택이 의미가 없다.
- **부족한 층**: DB · RLS · SERVER · STATE
- **위험도**: P1
- **기존 자산 재사용**: 없음(신규). 다만 GAP-06과 같은 트랜잭션 안에서 만들면 별도 동시성 처리가 필요 없다.
- **대표 승인 필요**: 예 (새 테이블)
- **구현 우선순위**: 2 · 범위 M

## 5. 대표 결정이 필요한 것 (6건)

기술로 정할 수 없다. 먼저 정해야 P1 구현을 시작할 수 있는 것부터 적었다.

### 지금 필요한 결정 (P1 착수에 필요)

**결정 1 · Purpose 목록을 무엇으로 할 것인가** ← GAP-16
현재 DB 4개와 화면 12개가 다릅니다. 어느 쪽이 맞습니까?
- (가) DB 4개가 맞다 → 화면을 4개로 줄인다
- (나) 화면 12개가 맞다 → DB에 8개를 추가한다
- (다) 둘 다 아니다 → 대표가 목록을 새로 정한다
그리고 이미 `values`로 저장된 1명을 어떻게 할지도 정해야 합니다.

**결정 2 · 자기이해 엔진을 어느 것으로 할 것인가** ← GAP-08 재정의
ECHO에는 자기이해 서버가 **두 개** 있습니다. 둘 다 정정·거절·맥락 기억을 구현하고 있습니다.

| | B 엔진 | A 엔진 |
| --- | --- | --- |
| 함수 | get-step-question v48 + echo-journey v26 | doit-understanding v4 |
| 방식 | 7단계 여정 대화 → 리포트 | 하루 기록 → AI 통찰 → 확인·정정·거절 |
| 검증 | FINAL100V4 실AI 100회 완료 | 미검증 |
| 데이터 | 대화 608건·메시지 11,856건 | 통찰 591건 |
| 현재 연결 | legacy 화면에만 (도달 불가) | Plan A 화면 (스위치 off) |

- (가) A 엔진을 제품으로 한다 → B는 보존만. GAP-01만 하면 된다
- (나) B 엔진을 Plan A 안으로 가져온다 → 어느 화면에서 7단계 대화를 할지 설계 필요 (범위 L)
- (다) 둘 다 쓴다 → 역할 분리 설계 필요

**작성자 의견**: (가). B 엔진은 마음 날씨 여정 전체와 묶여 있어 Plan A에 옮기려면 대공사입니다. A 엔진에 이미 같은 원칙이 구현되어 있고, 스위치만 켜면 동작합니다. B 엔진은 지우지 말고 자산으로 보존하면 됩니다.

### 나중에 필요한 결정 (P2 착수 전)

**결정 3** · 정보 점진 공개의 단계와 조건 (무엇을 언제 보여줄지)

## PHASE 3에서 대표가 승인해야 할 변경 — 최소 목록

이것만 승인하면 P0 3건이 닫힙니다. 되돌리기 어려운 것만 적었습니다.

| # | 변경 | 종류 | 되돌리기 | 왜 필요 |
| --- | --- | --- | --- | --- |
| 1 | 빌드에 `VITE_A_STRUCTURE_SERVER_ENABLED=true` 넣고 다시 배포 | Netlify 배포 | 쉬움 (이전 ZIP 재업로드) | GAP-01 · 사용자 데이터 유실 중단 |

**1번은 주의가 필요합니다.** 스위치를 켜면 지금까지 브라우저에만 있던 기록이 서버로 자동 이전되지 않습니다.

P1 3건(GAP-02·06·07)은 새 테이블 3~4개와 RPC 1~2개가 필요합니다.
결정 1·2가 끝난 뒤 PHASE 3에서 따로 승인받겠습니다.
