## C. "어떤 활동을 함께 하고 싶어요?"는 어디서 나왔나 — **B + C + D (서버 구조가 새 주제 이동을 시켰다)**

1. **서버가 새 주제로 넘어가게 정했다**
   - `pickStrategy`(689줄): 「그냥 편한친구 부담없이」는 12자라 `SHORT_ANSWER_MAX` 12 이하다. 그래서 전략이 CHANGE_DIRECTION(새 갈래)이 됐다.
   - 로그의 strategy 도 CHANGE_DIRECTION 이다.
2. **서버가 주제 칸을 골랐다**
   - `judgeCoveredTopics`(LLM) → `pickNextTopic(TOPICS 순서)` 순서로 정해진다. 결과는 direction 으로 프롬프트에 들어간다.
   - 화면 질문 카드 위에 **「상대가 알면 좋을 나」**가 보였다. 이 글자는 서버가 돌려준 topic 을 TOPICS 이름으로 바꿔 보여 주는 칸이다(CoreConversation 87~90줄). 그러니 서버가 준 topic 은 `self` 였다.
   - 주제 판정 AI 가 무엇을 "이미 나왔다"고 봤는지는 로그에 없다(확인 불가).
3. **프롬프트가 '같이 뭐 하고 싶은지'를 직접 가르친다**
   - CHANGE_DIRECTION 지침(321줄)의 유일한 예: `'잘 웃는 사람' → ack '잘 웃는 사람이 좋으시군요.' → '그런 사람이랑 만나면 같이 뭐 하고 싶어요?'`
   - QUESTION_STYLE(629줄)의 첫 규칙: "상대를 골라 주기 위해 알아야 할 것만 묻는다 — 어떤 사람이 좋은지, **같이 뭘 하고 싶은지**, 어떻게 만나고 싶은지, 상대가 알면 좋을 내 모습"
   - 나온 질문은 받은 방향(self)도 아니고, 예시 문장의 틀(받아 주기 + 같이 뭐 하고 싶어요)을 그대로 따랐다.
   - 그래서 **질문(같이 하고 싶은 것)과 화면의 주제 이름(상대가 알면 좋을 나)이 서로 다르게** 나갔다.
4. **"활동"은 프롬프트에서 쓰지 말라고 한 낱말인데 코드가 막지 않았다**
   - QUESTION_STYLE 에 "'활동'·'측면'·'가치관'·'내면' 같은 딱딱한 낱말 대신 일상 말"이 있다.
   - 하지만 코드의 `HEAVY_WORDS`(666줄)에는 가치관·측면·내면만 있고 '활동'은 없다.
5. **왜 서버 최종 검사를 통과했나**
   - 새 갈래의 필수 조건은 "받아 주는 첫 줄(ack)"뿐이다(no_bridge).
   - v15.2 에서 제가 넣은 `ackGrounded` 로, 첫 줄 「편한 친구를 원하시군요」가 원문과 '편한'·'친구'를 나눈다는 이유만으로 다리로 인정됐다.
   - 첫 줄이 있으면 `not_anchored`(질문이 방금 답의 말을 담는지)를 건너뛴다(1266줄).
   - 판정 AI 에게 준 자료에는 서버가 정한 strategy=CHANGE_DIRECTION 과 direction 이 들어 있다. 판정 지침에도 "새 주제로 넘어가는 질문은 방금 말을 받아 주고…이어질 때만 허용"이 있다.
   - 즉 **서버가 넘어가라고 시키고, 받아 주는 첫 줄만 있으면 넘어간 것을 '이어졌다'고 인정하는 구조**다.

**내 실수(먼저 밝힘):** v15.2 는 "질문이 안 나온다"를 "다리 인정 범위를 넓힌다"로 고쳤다. 그런데 "12자 이하면 서버가 주제를 바꾼다"는 구조 자체는 의심하지 않았다. 그래서 실패 모양이 "질문 없음"에서 "뜬금없는 질문"으로 바뀌었을 뿐, 원인은 같다.

## D. "활동?갑자기?"는 어떻게 분류·저장됐나

| 질문 | 결과 | 근거 |
|---|---|---|
| 관계 답변으로 저장됐나 | **예** — doit_records confirmed | DB |
| turn 을 올렸나 | **예** — 이번 회차 기록 2개(칸 2/5) | DB, 화면 `answered = roundRecords.length` |
| confirmed 후보에 들어갔나 | 이해 후보(insight)는 0개. 5턴 뒤 통합 카드 재료(이번 회차 답)에는 들어간다 | DB · `synthesisInput` |
| 다음 질문 생성 맥락에 들어갔나 | **예** — record 로 들어갔고, `ruleKind` 가 null 이라 사실인 답(answer)으로 처리됐다. 전략은 12자 이하라 다시 CHANGE_DIRECTION | 코드 1315·1326줄, 로그 |
| 연결 자격 「다섯 답」에 세나 | **예** — `informativeAnswer` 는 규칙이 못 가르면 답으로 센다 | RULES |

- **규칙이 못 잡은 이유**
  - 불만 규칙은 "같은 질문·또 묻네·반영해" 쪽이다. 되묻기 규칙은 "무슨 뜻·어렵다" 쪽이다.
  - "왜 갑자기 그걸 물어?"(주제가 튄 데 대한 문제제기)는 둘 다에 없다.
  - `^[^\s?]{1,6}\?+$` 는 물음표가 중간에 있는 「활동?갑자기?」와 맞지 않는다.
- **AI 분류가 answer 로 판정한 이유**
  - 분류 지침에 "answer … 엉뚱해도 사람·만남·자기 이야기면 답", "**애매하면 answer**"가 있다(1418줄).
  - 불만(complaint) 정의에도 "주제가 갑자기 바뀜"이 없다.
  - "애매하면 answer"는 v15.1 에서 진짜 답을 불만으로 잘못 버리던 것을 막으려고 넣은 것이다. 이번에는 반대쪽 오판을 냈다.
- **다음 질문이 실패한 이유**
  - 첫 줄이 앞 질문의 첫 줄과 비슷하다며 두 번 버려졌다(`ack_repeat`, 기계적인 「~시군요」 틀).
  - 그래서 방금 답에 머무는 전략(bridge_fallback)으로 넘어갔다.
  - 여기서는 질문이 방금 답 「활동?갑자기?」의 낱말을 나눠야 통과한다(`not_anchored`). 불만에 대한 좋은 질문일수록 그 낱말을 안 쓰므로 **통과할 수 없는 조건**이다.

| 15 | rejected(글자) `blockedByOverlap` | 거절 의미 금지 | – | 글자쌍 0.5/0.6·핵심어 | – | A1 후보1·2 (글자인지 의미인지 로그 구분 없음 — 확인 불가) | **예(거절)** |
| 16 | judge | 연결·목적·톤·정보 | 1~2 | – | allowed=false | 「활동」 질문을 허용 | 선택(아래 H) |
| 17 | 거절 의미 판정 | 거절 의미 금지 | 1 | – | blocked | 〃 | 예(거절) — 호출 횟수는 줄일 수 있음 |
| 18 | 시간·호출 예산 | 50초·9회 | – | 숫자 | 초과 | – | 예(안전) |

- 참고: 판정에 쓰는 거절 기록은 이 계정의 `"할 말이 없다."` 하나다(2026-09-24 00:20, 옛 버전이 지친 말을 이해 후보로 만든 것을 사용자가 거절함).
  - 이 한 줄 때문에 이 계정은 질문마다 거절 판정 LLM 이 1회 더 돈다.

## F. 분류

- **A. HARD SERVER RULE (서버가 꼭 가져야 함)**
  - 회차·칸 상태(0c)
  - 답 아닌 말은 칸·사실로 안 씀 — 판단은 LLM, 결과 처리는 서버
  - 이미 물은 질문(8), 거절 의미(15·17), 정정 우선(ACKNOWLEDGE_CORRECTION·superseded), 화면 안내문 재사용 금지(6)
  - AI 자기 신고 값(10), 저장 금지 입력(blockedContent), 금지어, 형식(3·4)
  - 예산(18)
- **B. SEMANTIC QUALITY (LLM 이 더 잘함)**
  - 자연스러운 연결, 받아 주기, 호기심, 가벼움·깊이 조절, 정보 증가, 목적 적합(16)
  - 턴 종류 판단(0b)
- **C. HEURISTIC (숫자·글자쌍·낱말 목록)**
  - 1(12자), 5(45자·낱말), 7, 9, 11, 12(+하위 6종), 13, 14
  - 2는 휴리스틱이 아니라 **칸 채우기 구조(D)**다.
- 이번 두 실패의 탈락 사유는 전부 C 층에서 나왔다(no_bridge, ack_repeat, not_anchored). 그리고 C 층의 1번(12자)이 새 주제 이동을 만들었다.
  - C 가 멀쩡한 후보를 막은 사례: FAIL #1 의 9개, A2 의 6개
  - C 를 통과한 이상한 질문: 「활동」

## G. 삭제·단순화 가능한 관문 (제안 · 아직 안 바꿈)

- **삭제**
  - 1 `pickStrategy` 의 12자 분기
  - 2 주제 판정 LLM + 칸 순서 방향
  - 12 no_bridge 와 첫 줄 하위 6종
  - 13 not_connected, 14 not_anchored, 9 restate, 11 no_reason, 7 why_chain
  - 5 의 낱말 목록·45자 → 프롬프트 지침으로만
- **LLM 한 번으로 합침**
  - 0b 턴 분류 + 후보 생성 + 받아 주기 판단을 한 호출로
  - 16 judge 는 정상 경로에서 빼고, 서버 필수 검사가 떨어진 뒤 다시 만들 때만(선택)
- **유지(서버 필수)**
  - 0c, 3, 4, 6, 8, 10, 15, 17(거절 기록이 있고 글자 검사가 애매할 때만), 18, 저장 금지 입력, 금지어
- **새 숫자는 넣지 않는다.** 남는 숫자는 모두 기존 값이다(REPEAT_SIM·REJECT_SIM·INSIGHT_MAX·예산).

## H. 새 Conversation Architecture (제안)

```
USER 답
 ↓
SERVER STATE LOAD (DB 읽기만, 지금 있는 표)
  이번 회차 원문 · 최근 Q/A 5쌍 · 맞다고 한 말 · 정정 · 거절 · 목적 · 이미 물은 질문
 ↓
ONE LLM TURN (호출 1회, JSON 구조 고정)
  turn_kind       : answer | unsure | correction | ask | meta | complaint | fatigue
  clue            : 방금 말에서 가장 궁금한 단서 — 사용자 원문에서 그대로 인용
  reply           : (필요할 때만) 짧은 반응 — 틀 문장 금지
  next_question   : 그 단서에서 한 걸음만 더 가는 질문 하나
  uses_rejected / assumes_unconfirmed / repeats_asked : 자기 신고
 ↓
SERVER HARD VALIDATION (결정적 · LLM 없음)
  turn_kind 결과 적용: answer·unsure·설명 붙은 correction 만 저장·칸 증가
                       ask·meta·complaint·fatigue 는 저장 0·칸 0·사실 0
  정정 충돌 · 거절 의미(기존 글자 검사) · 이미 물은 질문(기존 글자 검사) ·
  회차 상태 · 저장 금지 입력 · 금지어 · 형식(비어 있음·질문 하나) ·
  clue 가 사용자 원문 안에 실제로 있는가(글자 일치 — 숫자 문턱 없음)
 ↓ 통과                       ↓ 실패
USER                    떨어진 이유를 붙여 1회만 다시(예외 경로) → 그래도 실패면 명시적 실패
```

- **이 구조가 MASTER 를 지키는 이유**
  - LLM 은 후보만 만든다.
  - 저장 여부·칸 증가·거절·정정·이미 물음·상태는 서버가 결정한다.
  - 달라지는 것은 하나다. 서버가 "한국어 질문이 자연스러운가"를 글자쌍·숫자로 다시 판정하던 층(C)을 내려놓는다.
- **"활동?갑자기?"**
  - turn_kind=complaint 가 되어 저장 0, 칸 0이 된다.
  - 같은 호출의 next_question 이 직전 사용자 원문(「그냥 편한친구 부담없이」)의 단서에서 다시 출발한다. 기존 KIND_GUIDE 의 complaint 지침을 그대로 쓴다.
- **5칸 이후 추천 데이터**
  - 지금처럼 통합 카드(맞아요로 확인한 말)에서만 만든다.
  - 질문 단계에서 칸을 채우지 않는다. TOPICS 는 프롬프트에 "아직 모르는 것" 참고로만 남긴다(순서·방향 아님).
- **"우리 기술을 넣을 수 없나?"**
  - OpenAI 모델을 서버에 복사할 수는 없다.
  - ECHO 의 기술은 **기억·사실 상태·정정·거절·회차**를 서버가 쥐고, 그것을 매 호출에 정확히 넣고, 결과를 결정적으로 검증하는 층이다.
  - 언어의 자연스러움은 OpenAI 에 맡긴다.
  - JSON 구조를 더 단단히 받는 방법(OpenAI 의 JSON 스키마 고정 응답)은 쓸 수 있다. 다만 지금 모델에서 되는지는 **검증 필요**.
  - 모델 변경은 이번 제안에 넣지 않았다. 모델 변경은 대표 승인 사항이다.

## K. 회귀 위험

1. 휴리스틱을 빼면 LLM 이 딱딱하거나 긴 질문을 낼 수 있다.
   - 서버에 남는 것은 형식·반복·거절뿐이다.
   - 품질은 프롬프트와 대표 LEVEL 3 로만 확인된다.
2. 분류를 LLM 에 맡기면 "애매하면 answer"의 반대 오판(진짜 답을 불만으로 버림)이 돌아올 수 있다.
   - v15.1 에서 16개 중 14개 오판이 있었다(규칙 쪽).
   - 빠져나갈 문: 저장 0이어도 원문은 화면 입력창에 남기고 「답으로 저장하기」를 둔다(설계 필요).
3. 옛 앱(43차)과 새 서버의 호환: 옛 동작을 남겨 두면 깨지지 않는다. 새 앱과 새 서버는 같이 올려야 한다.
4. 거절 판정 LLM 을 줄이면 표현만 바꾼 거절 뜻이 통과할 수 있다. 글자 검사 + LLM 자기 신고 + (애매할 때만) 판정으로 보완한다.
5. 새 구조의 지연이 목표를 넘을 수 있다. 측정 전에는 PASS 로 판정하지 않는다.

## L. 검사 계획 (Mock 대량 금지)

1. 서버 결정 규칙만 가짜 AI 로 검사한다(각 1~2건).
   - ask·meta·complaint·fatigue 저장 0·칸 0, 거절 의미 차단, 이미 물은 질문 차단, clue 원문 일치, 5칸 끝, 다시 만들기 1회 뒤 명시적 실패
2. 호출 수 검사: 정상 턴 LLM 1회(가짜 AI 호출 횟수 세기).
3. 운영 관측: 요청마다 LLM 호출 수·호출별 ms·전체 ms 를 로그에 숫자로만 남긴다(원문 0).
   - 지금은 이게 없어 B 의 호출별 시간이 확인 불가다.
4. 대표 LEVEL 3: 「처음부터 시작하기」 → 5턴 → 질문마다 A 자연스럽다 / B 조금 어색 / C 뜬금없다·AI 같다.
   - 목표: C = 0.
   - 사용자가 AI 를 고쳐 주거나 질문 의도를 해석해 줘야 하는 순간이 있으면 FAIL.

   - 지금 실측으로는 판정할 수 없다. 새 구조 배포 뒤 운영 기록 20건 이상으로 잰다.

## 12. 지금 프롬프트의 호기심·사람다움·가벼움·한 걸음·감정 속도 — 원문 근거

| 항목 | 있나 | 원문 위치·순서 |
|---|---|---|
| curiosity | **우선순위로는 [구현 없음]** | QUESTION_STYLE 맨 끝 한 문장 "좋은 질문은 궁금하게 하고, 쉽게 답하게 하고, 한 가지를 더 알게 하고…". 판정(judge) 지침에는 없다 |
| 정보 우선 | 있음(1순위) | QUESTION_STYLE 첫 규칙 "상대를 골라 주기 위해 알아야 할 것만 묻는다 — 네 칸". judge 에 "목적 관문"·"정보 관문(새로 알게 되는 관계 정보가 없으면 불허)" |
| humanness | 있음(부차) | "말은 사람이 건네듯 가볍고 편안하게", "면접·설문·심문·심리상담처럼 캐묻지 않는다" |
| lightness | 있음 | "가볍게·짧게·심플하게" + 코드 45자·낱말 목록 |
| one-step | 있음 | "직전 답에서 단서 하나만 잡아 한 단계만 더" — 다만 CHANGE_DIRECTION 지침이 이것과 반대로 "hints 주제로 넘어간다"를 시킨다 |
| emotional pacing | 있음 | "사용자가 가볍게 답하면 가볍게 … 먼저 깊게 말했을 때만" |
| 기계적 받아 주기 | **프롬프트가 만든다** | ACK_STYLE 예 「조용한 곳이 편하시군요.」, CHANGE_DIRECTION 예 「잘 웃는 사람이 좋으시군요.」 → 운영 첫 줄 「편한 친구를 원하시군요.」. 새 갈래에서는 첫 줄이 필수(no_bridge)라 틀이 강제된다 |

결론: 지금 구조는 대표가 금지한 **DATA SLOT → QUESTION → NEXT SLOT** 구조다. 칸 순서, 12자 분기, 정보 관문이 그렇게 만든다. 호기심은 문장 하나로만 있고, 판정 기준에는 없다.
